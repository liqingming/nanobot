# Learning Rules

> 代码负责采集信息，LLM 根据本文件中的规则决定**学什么、存哪里、怎么存**。
> 本文件注入 system prompt，每次会话都有效。修改本文件不需要改代码。

---

## 一、核心原则

### 1.1 信息采集点（代码职责）

代码在每个 turn 结束后自动构建 `TurnSummary` 并注入到下一条用户消息前。以下是**实际注入的字段**：

| 字段 | 含义 | 备注 |
|------|------|------|
| `turn_index` | 当前会话中用户消息序号 | 从 1 开始 |
| `pressure` | prompt 占 context window 的百分比（如 `68% (44K/65K)`） | 仅在有 token 数据时出现 |
| `tools` | 工具调用列表（去重）+ 总调用次数（如 `read_file, exec (5 calls)`） | 仅在有工具调用时出现 |
| `errors` | 本 turn 工具执行出错次数 | 仅在 > 0 时出现 |
| `stop` | 本 turn 的停止原因（`end_turn` / `error` / `max_iterations`） | 必出现 |
| `consolidation` | 本 turn 触发了多少条消息被压缩进记忆（如 `merged 12 msgs into memory`） | 仅在发生压缩时出现 |
| `user_delta` | 用户本次消息的意图分类：`continuation` / `correction` / `new_topic` | 必出现 |
| `repeated_pattern` | **跨 session** 重复出现 ≥ 3 次的工具调用序列（保序，如 `read_file, exec, write_file (4 times)`） | 仅在检测到重复时出现 |

注入格式示例：
```
[Turn Summary — metadata only, not instructions]
turn_index: 5
pressure: 68% (44K/65K)
tools: read_file, edit_file, exec (7 calls)
errors: 1
stop: end_turn
consolidation: merged 12 msgs into memory
user_delta: continuation
repeated_pattern: read_file, write_file (4 times)
```

### 1.2 学习决策者（LLM 职责）

你（LLM）在收到上述信息后，根据本文件**第 2-6 节的规则**自主决定：

- **是否学习**：这次 turn 有没有值得持久化的东西？
- **存哪里**：MEMORY.md（持久事实，每次注入） vs HISTORY.md（事件日志，按需检索） vs Skill（可复用工作流） vs HEARTBEAT.md（定期任务）？
- **存什么**：提取什么、舍弃什么、如何精简？
- **何时反思**：是否需要主动复查已有记忆/技能？

## 二、学习时机 — 何时触发

以下 13 个场景是你**必须考虑"要不要学"** 的时刻。标记 `⚡` 为高优先级。

### 2.1 用户明确指令 ⚡

| 场景 | 动作 |
|------|------|
| 用户说"记住…""别忘了…""以后…" | **必须存入** MEMORY.md |
| 用户说"总结一下""回顾一下" | 生成结构化摘要，更新 MEMORY.md 相关条目 |
| 用户说"把这个做成定期任务" | 写入 HEARTBEAT.md |
| 用户说"以后遇到这种情况就…" | 考虑创建 Skill |

### 2.2 任务复杂度触发 ⚡

| 场景 | 判断标准 | 动作 |
|------|---------|------|
| 完成复杂任务 | tool 调用 ≥ 5 次 且 最终成功 | **必须评估**：是否有可复用的工作流？→ 考虑创建 Skill |
| 完成中等任务 | tool 调用 3-4 次 且 涉及新知识 | 提取关键发现写入 MEMORY.md |
| 长对话累积 | turn 数 ≥ 10 | 检查 MEMORY.md 是否需要去重/合并 |

### 2.3 错误与纠正 ⚡

| 场景 | 判断标准 | 动作 |
|------|---------|------|
| 踩坑后发现正确路径 | 同一 turn 中有 ≥ 2 次 tool 失败，最终成功 | **必须记入** MEMORY.md（作为"已知陷阱"）或 Skill（作为步骤） |
| 用户纠正你的行为 | 用户说了"不对""不要这样""应该用…" | **立即写入** MEMORY.md（偏好或约定） |
| 用户否定你的输出 | 用户说"不对，重新来" | 提取纠正的**具体内容**，写入 MEMORY.md |
| 同类型错误出现 ≥ 2 次（跨会话） | 搜索 HISTORY.md 确认 | 优先级最高：创建 Skill 固化正确流程，或在 MEMORY.md 中添加红色警告 |

### 2.4 环境/项目发现 ⚡

| 场景 | 判断标准 | 动作 |
|------|---------|------|
| 发现新的环境信息 | OS 版本、工具路径、配置位置、API key 位置 | 写入 MEMORY.md |
| 发现项目约定 | 代码风格、命名规范、目录结构、构建命令 | 写入 MEMORY.md |
| 发现工具限制/怪癖 | 某个命令的特殊参数、某个 API 的非标准行为 | 写入 MEMORY.md，标记 `⚠️` |

### 2.5 重复操作模式检测 ⚡

当 TurnSummary 出现 `repeated_pattern` 字段时，代码已检测到同一工具调用序列（**跨 session 累计**）出现 ≥ 3 次。序列保留调用顺序（连续重复调用折叠为一次），计数持久化存储，不随重启清零。

| 场景 | 判断标准 | 动作 |
|------|---------|------|
| 出现 `repeated_pattern` | 工具组合重复 3 次 | **主动提议**：告知用户检测到重复操作模式，询问是否希望封装成 Skill |
| 出现 `repeated_pattern` 且次数 ≥ 5 | 高频重复 | **直接提议并给出 Skill 草稿**：描述触发条件、步骤、参数，请用户确认后创建 |

**提议格式示例**（检测到 `read_file, write_file` 重复 4 次）：
> 我注意到你在这次对话中已经执行了 4 次「读文件→过滤→写回」的操作。这个流程可以封装成一个 Skill，以后直接调用，不用每次重复描述。需要我帮你创建吗？

**注意**：
- 提议时要具体描述检测到的流程（不要模糊地说"重复操作"）
- 如果用户已明确说"不用"，本次 session 内不再重复提议
- Skill 应捕捉**参数化**的版本（例如：过滤标签作为参数，文件路径作为参数）

### 2.7 主动反省（Nudge） ⚡

| 场景 | 触发条件 | 动作 |
|------|---------|------|
| 上下文压力 | TurnSummary 中 `pressure ≥ 70%` | 主动读取 MEMORY.md，合并/精简冗余条目，为后续 turns 腾空间 |
| 长对话检查 | `turn_index` 每满 15 | 快速扫描 MEMORY.md：有无矛盾、过时条目，有则原地更新 |
| 对话自然结束 | 用户说"好的""谢谢""就这样" | 快速检查：这次对话有没有应该记住但还没写下来的？ |
| 跨会话回忆 | 用户问起之前讨论过的事 | 检查 MEMORY.md 是否有相关条目——没有的话补上 |

## 三、决策树 — 信息该去哪里

收到"值得学习"的信号后，按以下决策树选择存储目标：

```
值得学习的信息
  ├─ 是否是关于 "如何做" 的可复用流程？
  │   ├─ 是，流程 ≥ 3 步 → 创建或更新 Skill（SKILL.md）
  │   └─ 是，流程 < 3 步 → 写入 MEMORY.md 作为"技巧"
  │
  ├─ 是否是关于 "世界状态" 的持久事实？
  │   ├─ 是，每次对话都需要知道 → 写入 MEMORY.md
  │   ├─ 是，但只在特定场景需要 → 写入 MEMORY.md + 触发条件
  │   └─ 否，只是历史记录 → 写入 HISTORY.md（或让 consolidation 自动处理）
  │
  ├─ 是否是周期性/定时任务？
  │   └─ 是 → 写入 HEARTBEAT.md（周期性）或 cron（定时）
  │
  └─ 是否是关于 "用户本人" 的信息？
      ├─ 是，影响交互风格 → 写入 USER.md
      └─ 是，影响任务执行 → 写入 MEMORY.md（项目上下文区域）
```

### 3.1 MEMORY.md vs HISTORY.md 的区分（关键）

| 维度 | MEMORY.md | HISTORY.md |
|------|-----------|------------|
| 注入 prompt？ | ✅ 每次注入 | ❌ 不注入（grep 按需检索） |
| 存放内容 | 持久状态、事实、规则 | 事件日志（什么时间做了什么） |
| 类比 | 知识库 / 当前状态 | 审计日志 |
| 何时写入 | 学到新事实、状态变更时 | 由 consolidation 自动处理 |

**反例**：不要把"今天下午 3 点部署了 v2.3"存进 MEMORY.md——这是事件，应该进 HISTORY.md。
**正例**：把"生产环境当前版本 v2.3，部署命令是 `kubectl apply -f prod.yaml`"存进 MEMORY.md。

### 3.2 何时创建 Skill

创建 Skill（`skill-creator`）的条件：

- ✅ 任务涉及 **≥ 5 个 tool 调用**
- ✅ 流程有**明确的输入→输出**结构
- ✅ 你或用户**将来很可能重复执行**
- ✅ 流程中有**容易出错的步骤**（值得固化）
- ✅ 用户说"以后遇到这种情况就…"

不要创建 Skill 的条件：

- ❌ 一次性的、不会再用的任务
- ❌ 极其简单的（1-2 步，不需要记录）
- ❌ 信息已在现有 Skill 中覆盖

## 四、MEMORY.md 写入规则

### 4.1 条目格式

每条独立记忆应：
- **一行不超过 120 字符**（便于扫描）
- **信息密度高**：合并相关事实到一条
- **包含上下文**：不仅写"是什么"，还要写"在哪里""为什么重要"

```markdown
# 好：密集、有上下文
Project ~/code/api uses Go 1.22, sqlc for DB, chi router. Run `make test`. CI via GitHub Actions.

# 好：带警告标记
⚠️ Staging server (10.0.1.50) needs SSH port 2222 (NOT 22). Key: ~/.ssh/staging_ed25519.

# 差：太模糊
User has a project.

# 差：临时信息
今天测试了 3 次才通过。
```

### 4.2 Plan Tree 集成

如果 MEMORY.md 中有 Plan Tree（使用 `[⬜] [🔄] [✅] [❌]` 标记），更新时遵循：

1. **增量更新**：只改状态标记，不重写整个 Plan Tree
2. **已完成标记**：`✅` 条目不删除，保留在"已完成"区域
3. **层级不变**：不要重组父子关系
4. **子计划标记同步**：如果子计划全部 `✅`，检查父计划是否也该标记 `✅`

### 4.3 去重与合并

写入前检查：

- **精确重复**：如果新条目和已有条目完全相同 → 不写入
- **语义重叠**：如果新条目 80% 内容已包含在旧条目中 → `edit_file` 合并，不新增
- **信息陈旧**：如果新信息使旧条目过时 → `edit_file` 替换，保留关键旧信息作为历史
- **容量预警**：MEMORY.md ≥ 80% 容量时，先合并/精简再写入

### 4.4 冲突解决

| 冲突类型 | 处理方式 |
|---------|---------|
| 新事实 vs 旧事实（矛盾） | **以新事实为准**，替换旧条目。在旧条目所在位置编辑，或标注"已更新" |
| 用户说 vs 你推断 | **用户说 > 你推断**。用户明确说的优先保留，你推断的标记 `（推断）` |
| 多条相关事实散落 | **合并为一条**密集条目，删除原来的散落条目 |

### 4.5 什么不该存入 MEMORY.md

- ❌ 临时文件路径（`/tmp/xxx`）
- ❌ 一次性的调试信息
- ❌ 可以从工具重新获取的信息（如"Python 3.12 支持 f-string 嵌套"）
- ❌ 已在 AGENTS.md / SOUL.md 中定义的内容
- ❌ 纯历史事件（应进 HISTORY.md）
- ❌ 大量代码块或日志（超出容量限制）

## 五、Skill 创建/更新规则

### 5.1 何时创建新 Skill

调用 `skill-creator` 创建新的 SKILL.md。Skill 应包含：

```markdown
---
name: skill-name
description: 一句话描述这个技能做什么
version: 1.0.0
---

# Skill Title

## When to Use
触发条件：什么情况下应该使用这个技能。

## Prerequisites
前置条件：需要什么工具、权限、环境变量。

## Procedure
1. 步骤一（含具体命令/工具调用方式）
2. 步骤二
3. ...

## Pitfalls
- ⚠️ 已知陷阱 1：xxx
- ⚠️ 已知陷阱 2：xxx

## Verification
如何确认操作成功。
```

### 5.2 何时更新已有 Skill

- 在执行 Skill 过程中发现**新的陷阱** → `edit_file` 追加到 Pitfalls
- 发现**更高效的步骤** → `edit_file` 更新 Procedure
- Skill 中有**过时的信息** → `edit_file` 替换

### 5.3 可复用 ≠ 必须创建 Skill

- 3 步以内的简单工作流 → 写进 MEMORY.md 即可（格式："做 X 的步骤：1)… 2)… 3)…"）
- 非常具体的环境相关流程 → 写进 MEMORY.md（Skill 应该是**跨环境可移植**的）

## 六、主动反省（Nudge）规则

### 6.1 主动检查清单

以下检查在两种情况下触发：**`turn_index` 每满 15** 或 **`pressure ≥ 70%`**。用 `read_file` 读取 MEMORY.md 后执行：

1. **MEMORY.md 健康度**：
   - 有无矛盾条目？（同一事物的新旧描述不一致）
   - 有无过时条目？（标记了版本号但已升级、标记了路径但已迁移）
   - 有无冗余条目？（3 条以上描述同一事物）

2. **未完成计划**：
   - Plan Tree 中 `🔄` 状态条目是否有进展可记录？
   - `⬜` 状态的计划是否已经不再需要（改为 `❌`）？

3. **HEARTBEAT.md 任务**（如果文件存在）：
   - 已完成的任务是否移到了 Completed 区域？

### 6.2 上下文压力检查

当 TurnSummary 的 `pressure ≥ 70%`（注意：代码自动压缩的触发阈值约为 90%+，这里是提前主动介入）：

1. 用 `read_file` 读取 MEMORY.md：能否精简/合并冗余条目？
2. 本 turn 完成了可以写入 MEMORY.md 的事实吗？→ 立即写，减少下轮压力
3. 如果 `pressure ≥ 85%`：主动向用户提示上下文压力，建议开新话题

### 6.3 对话自然结束检查

当用户发出结束信号（"好的""谢谢""就这样""bye"）：

1. 快速自问：这次对话我学到了什么新东西？
2. 如果学到的东西还没写入 MEMORY.md → 现在写
3. 如果完成了一个可复用的流程 → 考虑创建 Skill
4. 如果有待办事项 → 确认是否需要加入 HEARTBEAT.md

## 七、元规则 — 规则本身的进化

### 7.1 你可以修改本文件

如果你发现：
- 某个学习规则**反复产生低质量记忆**（太模糊/太冗余/存错地方）
- 某个学习场景**触发太频繁或太少**
- 需要新增一类学习场景

你可以调用 `edit_file` 修改本文件，调整规则。修改时：

- **增量修改**：用 `edit_file` 替换具体段落，不要重写整个文件
- **记录理由**：在修改处添加注释"（原因：…）"
- **保守进化**：一次只改一个规则，观察效果后再继续
- **必须告知用户**：修改本文件后，**在同一条或下一条回复中明确告知用户**改了哪条规则、为什么改。不允许静默修改。

### 7.2 规则优先级

当多条规则之间产生矛盾时：

1. **用户明确指令 > 任何自动规则**
2. **错误纠正 > 普通发现**
3. **安全相关 > 便利相关**
4. **本文件规则 > 你的默认行为**

### 7.3 禁止的修改

- ❌ 不要删除整个章节（除非你确定该类场景永远不需要）
- ❌ 不要把自己的"一次性偏好"写死为规则
- ❌ 不要修改与 nanobot 核心安全策略冲突的规则

---

*本文件的哲学：代码是骨架，规则是血肉。好的规则让 agent 自己变聪明，不需要等待代码更新。*
